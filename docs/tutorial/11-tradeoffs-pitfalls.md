# 11 設計取捨與踩坑紀錄

這一章保存最難從程式碼看出來的知識：當初為什麼這樣選、付出什麼代價，以及開發中實際踩過的坑。素材來自開發對話、設計文件與 commit 紀錄。

## 設計取捨

### 時鐘：只用 `now()`，不另做 Clock 介面

- **決策**：全系統只從 `now()`／Carbon 取時間；測試用 `travelTo()`，模擬器用 `Carbon::setTestNow()` 推進虛擬時間。
- **考慮過的選項**：自訂 `Clock` 介面，注入到每個服務。
- **理由**：📄 設計文件 §4.2：Eloquent 的 timestamp 本來就用 `now()`，另做一個 Clock 會有兩個時鐘，容易不同步。題目也明列 `setTestNow` 是可接受的做法。
- **代價**：時間是全域狀態，模擬器結束時一定要 `Carbon::setTestNow()` 還原（`SimulateCommand` 用 `finally` 處理）。Domain 層仍然把時間當參數傳入（例如 `allocate(..., $now)`），沒有直接呼叫 `now()`。

### Domain 層完全不碰資料庫

- **決策**：選桌、帶位、跳號、預估都是吃快照、吐結果的純 PHP。
- **考慮過的選項**：把規則寫在 Model 或 Service 裡。
- **理由**：📄 設計文件 §6：測試、預估、模擬器要共用同一份規則。
- **代價**：要寫一層「把資料庫狀態轉成快照」的程式（`app/Services/FloorRepository.php`），以及一堆小型值物件。

### 併發交給資料庫

- **決策**：三道防線：`IMMEDIATE` 交易、條件式更新、partial unique index。
- **考慮過的選項**：應用層加鎖（例如 cache lock）。
- **理由**：📄 開發第一輪討論時說明「SQLite 寫入時會鎖整個資料庫，搭配交易和條件式更新就擋得住，不需要額外的鎖服務」，使用者同意。
- **代價**：SQLite 所有寫入排隊執行；每晚 150 組的規模完全不是問題，但不適合高併發。

### 推播：交易提交後同步送出

- **決策**：`ShouldBroadcastNow` 加 `DB::afterCommit`，不用 queue worker。
- **考慮過的選項**：`ShouldBroadcast` 進佇列，由 worker 送出。
- **理由**：📄 設計文件 §5.13：少一個要啟動的程序，仍然做得到 2 秒內更新。實測最長 34 ms。
- **代價**：推播失敗時只能記 log，沒有自動重試。Reverb 沒啟動時，業務操作照常完成，但畫面要重新整理才會更新。

### 公開頻道推快照、私有頻道只推訊號

- **決策**：看板與顧客頁收完整快照（不含個資）；平板只收「有變動」，再用 HTTP 取資料。
- **理由**：📄 設計文件 §5.13：公開頻道誰都能訂閱，不能放姓名與手機。
- **代價**：平板每次變動多一個 HTTP 請求。

### 等候預估用帶位規則前推

- **決策**：預估器在虛擬時間上重複呼叫真正的 `SeatingAllocator`。
- **考慮過的選項**：公式法（前面組數 ÷ 桌數 × 平均用餐時間）。
- **理由**：📄 設計文件 §4.3：公式法反映不出跨佇列共用桌子、併桌、保護保留。
- **代價**：計算量較大；而且規則越偏向公平（保護越多），預估越難準。嚴格計數上線後，模擬的預估平均誤差從 6.2 升到 8.7 分鐘。

### 跳號定義改了三次

詳見 [08 章](08-algorithms.md) 的演變表。這裡記錄的是決策過程本身：

- **v1 資源版**是開發前和使用者討論後選的，理由是「嚴格版會讓小桌閒置」。
- 外部審查用模擬數據指出：v1 讓大組客人幾乎不會被計數。更重要的是，v1 的理由其實混淆了兩件事：「怎麼計數」與「保護時保留哪些桌子」。
- **v3** 把兩者拆開：計數用嚴格定義，保留範圍只限相關桌。

**教訓**：規則的理由要拆到最小單位檢查。「嚴格計數 → 小桌閒置」這個推論，中間其實藏著一個可以獨立選擇的步驟。

### 浪費上限依等候時間放寬

- **決策**：等滿 15 分鐘、而且沒有浪費 2 席以內的空桌時，允許浪費 3 席。
- **考慮過的選項**：上限直接改成 3；門檻 25 或 35 分鐘。
- **理由**：📄 commit `9ace858`：上限直接改 3，1 人客人可能去坐 4 人桌，佔掉後面 4 人組的位子。門檻實測 15、25、35 分鐘，整體入座與取消組數幾乎相同，差別只在 5–6 位與 7–8 位之間的取捨，維持 15 分鐘。
- **代價**：7–8 位的取消率從 6.7% 升到 16.7%（5 人組可以去坐 8 人桌了）。

### 模擬器用獨立資料庫

- **決策**：`simulation` 連線，每次重建 `database/simulation.sqlite`。
- **理由**：🔍 推斷：模擬要 `migrate:fresh`，在開發資料庫上做會清掉展示資料。
- **代價**：指令要記得在 `finally` 把 `database.default` 改回來，否則同一個程序後續的查詢會跑到模擬資料庫（有測試 `leaves the main database untouched`）。

## 踩坑紀錄

### 建議演算法把同一張桌子給了兩組人

- **症狀**：單元測試 `suggests the earliest party that fits` 失敗，兩組都被建議到 T4。
- **原因**：`$isFree` 用箭頭函式寫成 `fn (...) => isset($free[$t->id])`。PHP 的箭頭函式**以值捕捉**外部變數，之後 `unset($free[$id])` 對它沒有影響。
- **解法**：改成 `function (...) use (&$free)` 以參照捕捉。`app/Domain/Seating/SeatingAllocator.php`。
- **教訓**：在迴圈中修改、又要被 closure 看到的集合，用 `use (&$var)`。

### 系統自己的建議按下去被拒絕

- **症狀**：最終審查用 probe 測試重現：保護組被保留一張單桌時，系統建議另一組坐併桌，但按下叫號被拒「有空著的單桌可用」。模擬中這樣被拒了 4 次。
- **原因**：建議演算法把「保留給別人的保護桌」當成不空；叫號檢查為了讓錯誤訊息正確，把保護保留當成空著。兩邊對「空」的判斷不一致。
- **解法**：叫號檢查只把「被選中的」保護保留桌視為空，其他和建議演算法一樣視為不空。補上不變式測試「系統建議依序叫號必須全部成功」。commit `0d4c311`。
- **教訓**：同一個概念（「空」）在兩個模組各寫一次，遲早會不一致。

### 模擬器把 bug 藏起來

- **症狀**：上一個 bug 在模擬中實際發生了 4 次，但模擬器輸出完全正常。
- **原因**：模擬器的 `attempt()` 把業務例外靜默吞掉（`catch (QueueTableException) {}`），違反「禁止無聲吞掉 exception」的原則。
- **解法**：依例外類別計數並輸出；有任何系統建議被拒就判定「建議一致性 FAIL」。commit `0d4c311`。
- **教訓**：驗證工具本身更不能吞例外；它存在的目的就是讓問題被看見。

### 模擬器拿過時的建議卡叫號

- **症狀**：修好上一個問題後，seed 3 仍有 1 次建議被拒。
- **原因**：暫時印出被拒時的狀態才找到：模擬器一次取得整批建議後連續叫號。保護組被叫號後，原本保留給他的另一張單桌被釋放；同一批裡另一組的併桌建議，因為現在有空的單桌而不再合法。
- **解法**：模擬器改成和平板一樣，每叫一組就重新取得建議。`app/Simulation/SimulationRunner.php`。
- **教訓**：模擬要盡量貼近真實的使用方式。平板每次操作後都會重新載入，模擬器也應該如此。

### 預估器少算跳過次數

- **症狀**：手算案例預期 Y 等 `[35,55]` 分，實際算出 `[10,30]`。
- **原因**：前推時，同一輪先分出去的桌子在後面判斷「被跳過」時仍被當成空桌，所以前面的組看起來「還有桌子可坐」，沒被計數，也就沒進入保護。
- **解法**：每分配一組，就把他的桌子在本輪的快照中標成已佔用。commit `9a20261`。
- **教訓**：先寫出「錯誤實作會算出什麼」的手算預測，失敗時看到的值正好是預測的錯誤值，就能確定根本原因。

### 同一毫秒取號，重新排入排到第 2 位

- **症狀**：外部審查指出；測試在凍結時間下重現。
- **原因**：同一毫秒取號的兩組 `position_key` 相同，取中點還是同一個值，再依 id 排序，重新排入的組（id 較小）排到前面。模擬器每一步凍結時間，同一步到達的客人就會撞值。
- **解法**：`TicketService::nextPositionKey()` 保證同營業日內嚴格遞增。commit `9ace858`。

### 歷史資料的等候長達 391 分鐘

- **症狀**：報表頁實際打開後，歷史資料的 A 佇列平均等 87 分鐘、最長 391 分鐘。
- **原因**：設計時定「每晚 100–150 組」，但 20 張桌、9 小時的容量撐不住每晚 147 組。
- **解法**：歷史產生量調為每晚約 90–125 組（`database/seeders/HistorySeeder.php`）。commit `a9e99c4`。
- **教訓**：測試只驗證「不重疊、不超過容量」，驗證不了「數字合理」。要實際打開頁面看。

### 窄體字型裡 O 和 0 分不出來

- **症狀**：平板截圖上戶外桌 `O01` 看起來像 `001`。
- **解法**：戶外桌代號改為 `T01`–`T05`（Terrace）。commit `0f03b03`。
- **教訓**：選了有個性的字型，要檢查專案裡實際會出現的字元組合。

### Starter Kit 拿掉功能後前端建置失敗

- **症狀**：關閉 Fortify 的 2FA、Passkey 後，`npm run build` 找不到 `@/routes/two-factor` 等模組。
- **原因**：Wayfinder 依現有路由產生 TypeScript 路由函式；功能關掉，路由消失，但設定頁元件還在引用。
- **解法**：整組移除用不到的設定頁、元件與測試。commit `1d44e5e`。

### PHP 8.3 裝不起來

- **症狀**：準備 CI 時發現 Pest 5、PHPUnit 13、Symfony 8 都要求 PHP 8.4，與題目「PHP 8.3 以上」衝突。
- **解法**：`composer.json` 設 `config.platform.php = 8.3.0`，讓 composer 解析出 8.3 也能裝的組合。commit `5371d60`。
- **教訓**：「最低支援版本」要在 CI 上實際跑一次最低版本才算數。

### 只有全新 clone 才抓得到的格式錯誤

- **症狀**：本機檢查全過，全新 clone 照 README 安裝後，CI 檢查失敗在 README 的 Markdown 格式。
- **原因**：前端格式檢查也涵蓋 Markdown，而 README 是最後才加的。
- **解法**：用格式化工具整理 README。commit `05b088d`。
- **教訓**：交付前用全新 clone 照 README 走一遍，能抓到「我的機器上可以」類的問題。

### 測試中的陷阱

| 症狀 | 原因 | 解法 |
|---|---|---|
| JSON 請求的測試一直被導去選平板 | Laravel 測試的 `postJson` 預設不帶 cookie | `actingAsHost()` 加上 `withCredentials()` |
| 新頁面還沒 build，HTTP 測試就 500 | 整頁渲染需要 Vite manifest | `tests/TestCase.php` 呼叫 `withoutVite()` |
| 想測排程，`schedule:run` 卡住不動 | 秒級排程會在同一分鐘內反覆執行並等待，時間凍結時永遠等不到下一分鐘 | 不跑 `schedule:run`，直接取出排程事件斷言間隔並執行 |

## 潛在風險

以下沒有實際發生，但值得注意（🔍 推斷，或來自審查的延後處理清單）：

- **店長營業中修改桌位**：不會觸發狀態同步，保護保留與預估會過時，直到下一次任何操作。
- **推播合併旗標**：交易 rollback 後，`QueueBroadcaster` 的 `$pending` 不會清除；在長時間執行的程序中，該營業日後續的推播可能被抑制。
- **每次讀取都開寫入交易**：`ExpireNoShows` 讓看板、顧客頁每次讀取都開一次 `IMMEDIATE` 交易，即使沒有任何過號。
- **9 人以上的大組**：受桌位配置限制，模擬取消率約 92%。
