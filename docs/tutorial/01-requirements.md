# 01 需求分析

這一章整理「系統要解決什麼問題」。題目原文完整保存在 `docs/requirements.md`，這裡把它拆成可追溯的編號，並標出哪些是題目明文、哪些是開發中補上的決定。

## 背景與目標

> 📄 依據：`docs/requirements.md`「案名與客戶背景」

一間約 80 個座位的熱炒店，晚餐尖峰常有 30 組以上客人在門外等。目前用紙本寫號碼、店員喊號，常發生**跳號**、**等很久的客人被插隊**的爭執。營業時間 17:00 到凌晨 02:00，門口有兩位帶位人員各拿一台平板，客人也可以用手機掃 QR Code 遠端取號。

所以系統的核心目標不是「電子化叫號」，而是建立一條**公平、可稽核**的候位佇列：誰先來、誰被跳過幾次、哪台平板在幾點做了什麼，都要查得到。

> 📄 依據：開發對話中使用者說明「交付的目的是作品跟面試用」

因此開發時的優先順序是：驗收標準每一條都要有可指認的證據（測試、README、模擬器輸出），架構要能在面試中講解；現場營運細節做到不卡即可。

## 使用者與角色

| 角色 | 裝置 | 主要工作 | 登入方式 |
|---|---|---|---|
| 帶位人員 | 平板 ×2 | 看建議叫號、入座、桌況操作、代客取號 | 帳號密碼 + 選擇是哪一台平板 |
| 店長 | 任一裝置 | 桌位設定、建立帳號、看營業日報表 | 帳號密碼 |
| 顧客 | 手機 | 遠端取號、看自己的號碼與預估、自行取消 | 不需帳號，用取號時拿到的連結 |
| 門口看板 | 螢幕 | 顯示各佇列叫到的號碼與等候組數 | 不需登入 |
| 系統 | 排程 | 叫號滿 3 分鐘自動過號 | — |

> 📄 依據：`docs/requirements.md`「假設事項」：帳號由店長建立、顧客以連結查看狀態

## 功能需求

| 編號 | 需求 | 來源 |
|---|---|---|
| FR-01 | 桌子有編號、座位數、區域（室內、戶外、吧台），以及可併桌的相鄰桌 | 📄 題目功能需求 1 |
| FR-02 | 桌子狀態：可用、用餐中、清桌中、停用 | 📄 題目功能需求 1 |
| FR-03 | 輸入人數、稱呼、手機取號；管道有門口平板與手機遠端 | 📄 題目功能需求 2 |
| FR-04 | 依人數分 A（1–2）、B（3–4）、C（5–6）、D（7+）四個佇列，號碼為字母加三位數，例如 `B012` | 📄 題目功能需求 2 |
| FR-05 | 號碼每個營業日從 001 開始，不重複、不跳號 | 📄 題目功能需求 2、驗收 2 |
| FR-06 | 同一支手機在同一營業日只能有一筆等候中的號碼，再取被拒並說明原因 | 📄 題目功能需求 2、驗收 3 |
| FR-07 | 依近 14 天同時段、同佇列的歷史用餐時間與目前桌況，以區間預估每組還要等多久 | 📄 題目功能需求 3 |
| FR-08 | 入座、離開、過號時即時更新所有人的預估 | 📄 題目功能需求 3 |
| FR-09 | 桌子空出時建議叫誰、帶到哪桌：浪費座位最少，必要時併相鄰兩桌 | 📄 題目功能需求 4、驗收 4 |
| FR-10 | 輪到的客人沒有適合的桌子時可以讓後面的人先入座，但同一組最多被跳過 3 次，之後保留下一張適合的桌子給他 | 📄 題目功能需求 4、驗收 5 |
| FR-11 | 叫號後 3 分鐘未報到即過號；可重新排入佇列第 3 位，每組只能一次 | 📄 題目功能需求 4、驗收 6 |
| FR-12 | 門口看板顯示各佇列目前叫號與等候組數 | 📄 題目功能需求 5 |
| FR-13 | 顧客頁顯示自己的號碼、前面幾組、預估等候，可自行取消 | 📄 題目功能需求 5 |
| FR-14 | 看板與顧客頁透過 WebSocket 在 2 秒內更新 | 📄 題目功能需求 5、驗收 7 |
| FR-15 | 前面剩 2 組時寫入一則「即將輪到」通知，不重複 | 📄 題目功能需求 5、驗收 8 |
| FR-16 | 平板可看到所有桌況並執行入座、離開、清桌完成、停用 | 📄 題目功能需求 6 |
| FR-17 | 每次狀態變更留下時間、操作人員、哪一台平板 | 📄 題目功能需求 6、驗收 13 |
| FR-18 | 營業日報表：取號數、入座數、過號率、取消率、各佇列平均與最長等候、預估誤差、各桌周轉、被跳過次數分布；可匯出 CSV | 📄 題目功能需求 7、驗收 12 |
| FR-19 | artisan 指令以加速時鐘模擬一晚，輸出預估誤差、最長等候、跳過是否都不超過 3 次、桌位使用率 | 📄 題目功能需求 8、驗收 11 |
| FR-20 | 等候滿 15 分鐘、且沒有浪費 2 席以內的空桌時，允許坐浪費 3 席的桌子 | 📄 外部審查建議，使用者貼上後要求實作（commit `9ace858`） |
| FR-21 | 模擬器依人數分組輸出取消率與含取消的最長等候 | 📄 外部審查建議（commit `d89a713`） |

## 非功能需求

| 編號 | 需求 | 來源 |
|---|---|---|
| NFR-01 | PHP 8.3 以上、Laravel 12 以上、Vue 3 + Vite、SQLite，不需要 Docker | 📄 題目「技術與平台限制」 |
| NFR-02 | 時間相關邏輯一律透過可注入的時鐘，測試不得等待真實時間 | 📄 題目「技術與平台限制」 |
| NFR-03 | 同一張桌子不會同時帶入兩組；同一組不會帶入兩張桌子 | 📄 題目驗收 9 |
| NFR-04 | 測試至少 45 個，全數通過 | 📄 題目驗收 14 |
| NFR-05 | CSV 用 Excel 開啟中文不亂碼 | 📄 題目驗收 12 |
| NFR-06 | 資料量以每晚 150 組、保存一年為上限 | 📄 題目「假設事項」 |
| NFR-07 | 公開的 WebSocket 頻道不得送出姓名、手機 | 🔍 推斷：題目沒寫，但看板與所有顧客共用公開頻道，送出個資是明顯的隱私問題，開發時列為「反目標」（設計文件 §2） |
| NFR-08 | 平板與手機透過店內區網連到單一主機 | 📄 題目「假設事項」 |

## 範圍外

> 📄 依據：`docs/requirements.md`「假設事項」與設計文件 §2「非目標」

- 事先訂位。
- 簡訊、LINE 等外部通知（「即將輪到」只寫入通知紀錄表）。
- 三張以上併桌、入座後換桌。
- 多店、多語系、正式環境部署（HTTPS、反向代理）。

## 開發中補上的規則

題目有幾處沒講清楚，開發前和使用者討論後才定案。這些是理解程式碼最需要知道的背景：

| 題目沒講清楚的地方 | 最後的決定 | 來源 |
|---|---|---|
| 營業到凌晨 02:00，跨午夜怎麼算「同一營業日」 | 以台灣時間 06:00 切日 | 📄 設計文件 §5.1，對話中使用者同意 |
| 跨佇列共用桌子時，「誰先」怎麼比 | 用取號時間做全域順序，跨四個佇列比較 | 📄 設計文件 §5.4 |
| 「適合的桌子」的定義 | 坐得下且浪費不超過 2 席；等滿 15 分鐘可放寬到 3 席 | 📄 設計文件 §5.7 與修訂 |
| 「被跳過」怎麼算 | 經過三次演變，最後依題意嚴格計數，見 [08 章](08-algorithms.md) | 📄 對話紀錄、commit `455fb5b`、`9a20261`、`9ace858` |
| 重新排入「第 3 位」在只剩 2 組或更少時怎麼辦 | 剛好 2 組 → 排第 2 組後面；不到 2 組 → 排到最後 | 📄 設計文件 §5.4（設計審查後補上） |

## 未解決或待確認的需求問題

- **9 人以上的大組幾乎坐不到位子**：模擬中取消率約 92%。瓶頸在桌位配置（只有 I10–I11–I12 一串相鄰桌坐得下），不是跳號規則。要改善得調整桌位或開放大組預約。📄 README 第 10 節「已知限制」。
- **報表最長等候取整數**：設計文件 §5.15 寫小數 1 位，實作是整數。列在最終審查的延後處理清單（對話紀錄）。
