# 題目：餐廳候位叫號與帶位系統（QueueTable）

## 案名與客戶背景
一間約 80 個座位的熱炒店，晚餐尖峰常有 30 組以上客人在門外等，目前用紙本寫號碼、店員喊號，常發生跳號、等很久的客人被插隊的爭執。店家營業時間 17:00 到凌晨 02:00，門口有兩位帶位人員各拿一台平板，客人也可以用手機掃 QR Code 遠端取號。

## 功能需求
1. **桌位設定**
   - 每張桌子有編號、座位數、區域（室內、戶外、吧台），以及可以和哪些相鄰桌子併桌。
   - 桌子狀態：可用、用餐中、清桌中、停用。
2. **取號**
   - 客人輸入人數、稱呼、手機號碼後取號，取號管道有門口平板與手機遠端兩種。
   - 依人數分成四個佇列：A（1–2 人）、B（3–4 人）、C（5–6 人）、D（7 人以上），號碼格式為佇列字母加三位數，例如 `B012`。
   - 號碼在每個營業日從 001 開始。
   - 同一支手機在同一營業日只能有一筆等候中的號碼。
3. **等候時間預估**
   - 依近 14 天同時段、同佇列的歷史用餐時間，以及目前各桌的入座時間，預估每一組客人還要等多久，以區間表示，例如「約 15–25 分鐘」。
   - 有客人入座、離開、過號時，即時更新所有人的預估。
   - 預估方法寫在 README，並以模擬器量測預估誤差。
4. **叫號與帶位建議**
   - 有桌子空出時，系統建議要叫哪一組、帶到哪一桌：優先選座位數最接近、浪費座位最少的桌子，必要時建議併桌。
   - 輪到的客人沒有適合的桌子時，可以先讓後面人數較少的客人入座，但同一組客人最多被跳過 3 次，之後系統保留下一張適合的桌子給他。
   - 叫號後 3 分鐘內沒有報到，視為過號；過號的客人可以重新排入，位置為目前佇列的第 3 位，每組只能重新排入一次。
5. **即時看板與顧客頁面**
   - 門口看板顯示各佇列目前叫到的號碼與等候組數。
   - 客人的手機頁面顯示自己的號碼、前面還有幾組、預估等候時間，並可以自行取消。
   - 看板與顧客頁面透過 WebSocket 即時更新，不需要重新整理。
   - 前面剩 2 組時，系統產生一則「即將輪到」通知，寫入通知紀錄表即可，不需要真的發送簡訊。
6. **桌況管理**
   - 帶位人員在平板上看到所有桌子的狀態與入座時間，可以執行入座、離開（轉為清桌中）、清桌完成、停用。
   - 每次狀態變更都留下紀錄：時間、操作人員、哪一台平板。
7. **營業日報表**
   - 報表內容：取號數、入座數、過號率、取消率、各佇列平均與最長等候時間、預估誤差（平均絕對誤差）、各桌周轉次數、被跳過的次數分布。
   - 可以匯出 CSV。
8. **尖峰模擬器**
   - 提供 artisan 指令，以加速時鐘模擬一個晚上：客人依設定的到達率（各時段不同）抵達、人數依設定的分布、用餐時間依歷史分布，部分客人過號或中途取消。
   - 模擬結束後輸出：預估誤差、最長等候、跳過次數是否都不超過 3 次、桌位使用率。

## 技術與平台限制
- PHP 8.3 以上，Laravel 12 以上。
- 前端使用 Vue 3（Inertia 或獨立 SPA 皆可），以 Vite 建置。
- 資料庫使用 SQLite，需附 migration 與 seeder。
- 即時推播使用 Laravel Reverb，或其他不需要 Docker 的 WebSocket 方案。
- 時間相關邏輯一律透過可注入的時鐘取得（例如 Carbon 的 `setTestNow` 或自訂 Clock 介面），測試不得等待真實時間。
- 測試使用 Pest 或 PHPUnit。不需要 Docker。

## 驗收標準
1. 依 README 執行 `composer install`、`npm install` 與啟動指令後，可以開啟帶位平板頁、門口看板、顧客取號頁，seeder 已建立 20 張桌子與近 30 天的歷史用餐紀錄。
2. 取號後號碼格式正確，同一營業日、同一佇列的號碼不重複、不跳號，並有測試。
3. 同一支手機在同一營業日已有等候中的號碼時，再次取號被拒絕並顯示原因，並有測試。
4. 帶位建議選擇浪費座位最少的桌子；只有併桌才坐得下時建議併桌，且只會併可以相鄰的桌子。需有測試。
5. 同一組客人被跳過第 4 次之前，系統保留下一張適合的桌子給他，並有測試。
6. 叫號後 3 分鐘未報到即轉為過號；重新排入時位置為佇列第 3 位，第二次過號不能再重新排入。以可注入的時鐘測試。
7. 客人入座、離開、取消時，看板與所有顧客頁面在 2 秒內更新，不需要重新整理。
8. 前面剩 2 組時，通知紀錄表中剛好產生一則「即將輪到」通知，不會重複產生，並有測試。
9. 同一張桌子不會同時被帶入兩組客人；同一組客人不會被帶入兩張桌子。需有測試。
10. 預估等候時間的計算，與測試中以固定歷史資料手算的結果一致。
11. 模擬器跑一個晚上（17:00 到 02:00）後，輸出的預估平均絕對誤差與最長等候時間寫在 README，且模擬中沒有任何客人被跳過超過 3 次。
12. 營業日報表的各項數字與測試中手算的結果一致；CSV 用 Excel 開啟中文不亂碼。
13. 所有狀態變更都有操作紀錄，包含時間、操作人員與平板識別。
14. 測試至少 45 個，全數通過。

## 假設事項
- 店家位於台灣，所有時間以台灣時間為準。
- 只處理現場候位，不處理事先訂位。
- 帶位人員帳號由店長建立，以帳號密碼登入；顧客不需要帳號，以取號時取得的連結查看狀態。
- 併桌只考慮兩張相鄰桌子合併，不處理三張以上。
- 同一組客人入座後不換桌。
- 不串接簡訊、LINE 或任何外部通知服務。
- 店內只有一台主機執行系統，兩台平板與顧客手機透過網路連線。
- 資料量以每晚 150 組客人、保存一年為上限。
